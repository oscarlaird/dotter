Table \ref{tab:architecture} shows the architecture of Dotter.
At its heart is the ``TRIE'' (chapter \ref{chap:trie}) in the rightmost column, 
which is a Bayesian prefix trie which maintains
a calculation of the posterior probability of every prefix.
The other elements of the system may be separated into the Likelihood Cycle and the Prior Cycle.

Every element in Table \ref{tab:architecture} is discussed in detail in its own chapter.

\section{The Likelihood Cycle}
The Likelihood Cycle refers to the series of steps by which we elicit
a signal from the user and then interpret that signal to update our
posterior probabilities. It has seven steps,
\begin{enumerate}
  \item \textbf{Determine Visible Nodes} (chapter \ref{chap:determine-visible-nodes}): we determine which prefixes should be visually displayed
  by checking which prefixes have a posterior probability exceeding the visibility threshold (e.g. 2\%).
  \item \textbf{Render Trie} (chapter \ref{chap:render-trie}): here we draw the visible prefixes to the screen, connecting parent nodes to their
  children with smooth curves.
  \item \textbf{Optimize Stimulus Parameters} (chapter \ref{chap:optimize-stimulus-parameters}): in this step we assign timers to every prefix. 
  We want to maximize the information gain from the user's signal which is accomplished by making the timers as
  far apart from each other as possible (in a formal sense). This helps to make the user's selection unambiguous.
  \item \textbf{Render Stimulus} (chapter \ref{chap:render-stimulus}): we draw the timers to the screen.
  \item \textbf{Detect Response} (chapter \ref{chap:detect-response}): we detect the user's signal. It is trivial to detect a keypress; detecting the exact timing of a blink is a more sophisticated problem.
  \item \textbf{Likelihood Result} (chapter \ref{chap:likelihood-result}): we compare the detected user signal to the timers that were assigned in step 3.
  This gives us a likelihood score for each prefix.
  \item \textbf{Likelihood Update} (chapter \ref{chap:likelihood-update}): we update the trie to reflect the received likelihoods.
  Performing this update in a lazy and efficient manner is a central technical
  challenge of Dotter.
  (This is an ``update'' in the traditional bayesian sense.)
\end{enumerate}

\section{The Prior Cycle}
The Prior Cycle refers to the series of steps by which we 
query a large language model to refine our prior probabilities
and incorporate those results into our posterior beliefs.
It has four steps,
\begin{enumerate}
  \item \textbf{Determine Most Likely Break Nodes} (chapter \ref{chap:determine-most-likely-break-nodes}): we determine which nodes are most likely
  to a break between tokens in the tokenization of the user's target text.
  \item \textbf{LLM Query} (chapter \ref{chap:llm-query}): we query the large language model to predict the distribution over the next token for the prefixes
  identified in the previous step.
  \item \textbf{LLM Result} (chapter \ref{chap:llm-result}): we receive the result from the language model.
  \item \textbf{Prior Update} (chapter \ref{chap:prior-update}): we update the trie to reflect the received prior probabilities.
  Performing this update in a lazy and efficient manner is a central technical
  challenge of Dotter.
  (This is not truly an ``update'' in the traditional bayesian sense, since normally our priors are fixed.)

\end{enumerate}
